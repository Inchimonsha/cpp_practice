# m12_parallel_gpu/ex02_task_scheduling — планирование задач по графу зависимостей

> Модуль m12_parallel_gpu · Сложность ★★★ · C++23 · Запуск: `./run.ps1 m12_parallel_gpu/ex02_task_scheduling`

## Теория

Многие задачи распараллеливаются не «по элементам массива», а по **графу
зависимостей** (data-flow / DAG): задача готова к выполнению, когда готовы все её
предшественники. Классический пример — ромб:

```
    0     1
     \   / \
       2     \
       |      \
       3       4
```

Заготовка планировщика:

1. Считаем **полустепень захода** (indegree) каждой задачи.
2. Задачи с indegree 0 — в очередь готовых.
3. Пул рабочих потоков берёт готовую задачу, выполняет, записывает результат и
   **уменьшает indegree** последователей; те, у кого стало 0, попадают в очередь.

Порядок выполнения недетерминирован, но **результаты** — детерминированы
(зависимости гарантируют, что входные значения уже посчитаны). Это свойство
называют *data-race free by construction*.

Другой способ выразить тот же граф — цепочка `std::future`/`std::async`
(композиция через `.get()` в продолжении).

## Синтаксис

```cpp
graph.add([](const std::vector<double>&) { return 2.0; }, {});        // istochnik
graph.add([](const std::vector<double>& in) { return in[0] * in[1]; },
          {0, 1});                                                    // zavisit ot 0 i 1
std::vector<double> results = graph.run(/*workers=*/4);

auto base = std::async(std::launch::async, [] { return 21; });
auto doubled = std::async(std::launch::deferred, [&] { return 2 * base.get(); });
int value = doubled.get();                                            // 42
```

## Подводные камни

- **Потокобезопасность очереди готовых**: `std::queue` + `std::mutex` +
  `std::condition_variable`; проверяйте предикат в `wait` в цикле.
- **Чтение результатов предшественников** должно происходить после их записи —
  синхронизируйте через тот же мьютекс (публикация + захват дают
  happens-before).
- **Завершение рабочих**: условие выхода — «все задачи выполнены И очередь
  пуста», иначе потоки уснут навсегда. Не забудьте `notify_all`.
- **Владение потоками**: `std::jthread` присоединяется в деструкторе — не
  возвращайте ссылки на локальные данные, пока потоки живы (дождитесь
  завершения до выхода из функции).
- Циклы в графе недопустимы: часть задач никогда не станет готовой (проверяйте
  на этапе построения).

## Задача

Реализовать `TaskGraph` с методом `run(workers)`, который исполняет задачи в
порядке зависимостей на пуле потоков, и вывести результаты. Дополнительно
показать композицию `std::future`. Ожидаемые результаты ромба:
`task 0 = 2`, `task 1 = 3`, `task 2 = 6`, `task 3 = 60`, `task 4 = 8`,
`future composition = 42`.

## Где применяется

- Планировщики сборки (Make/Ninja/Bazel), конвейеры обработки данных,
  обучение нейросетей (граф вычислений), асинхронные веб-обработчики.

## Проверка

Вывод: пять строк `task N = ...` (2, 3, 6, 60, 8), `future composition = 42`,
`task scheduling done`. Код возврата `0` при совпадении, иначе `1`.

## Решение

См. `ex02_task_scheduling.cpp`. Пул рабочих — `std::jthread`; готовность задач
отслеживается снижением indegree при публикации результата под мьютексом.
