# Архитектура: prj01 — Arcade Game

## 18. Архитектура

Двухслойная:

```
┌─────────────────────────────────────────────┐
│ Game (SFML)    окно, цикл, ввод, рендер      │
│   └─ Renderer: Entity/Aabb → sf::Rectangle   │
├─────────────────────────────────────────────┤
│ Модель (чистый C++20, без SFML)             │
│   Score / Player / FallingObject             │
│   Aabb (коллизии)                           │
└─────────────────────────────────────────────┘
```

Правило связи: **модель не знает о SFML**, рендер не знает о правилах игры.
`Game` — композиция: владеет моделью и рисует через тонкий «перевод» в SFML.
Зависимость направлена только от `Game` вниз к модели.

Почему так: модель тестируется без окна (`ctest`), игра не зависит от FPS
(время — параметр `update(dt)`), замена рендера (например, терминальный вывод
логики для плейтеста) — тривиальна. Это осознанный простой вариант разделения
симуляции и визуализации (полноценно — th34).

## 19. Основные подсистемы

| Подсистема | Классы (модель) | Ответственность |
|---|---|---|
| Игровое состояние | `GameState` (enum) | игра / game over / restart |
| Сущности | `Entity`, `Player`, `FallingObject` | позиция, размер, движение |
| Счёт и жизни | `Score` | очки, жизни, рекорд |
| Коллизии | `Aabb` | пересечение прямоугольников |
| Рендер | `Game::render()` | перевод модели в SFML-объекты |
| Сохранение | `Score::save/load` | рекорд в `record.txt` |

## 20. Модель данных

```
Player       { Aabb bounds; float speed; }
FallingObject{ Aabb bounds; Kind kind; float vy; }
Kind         = good | bad
Score        { int score; int lives; int record; }
GameState    = Playing | GameOver
```

Позиции — во float (пиксели), размеры — во float. `Aabb` хранит `(x, y, w, h)`
и умеет отвечать на пересечение. `Vec2` берётся из `common/math/vec2.hpp`.

## 21. Жизненный цикл приложения

```
main()
  └─ Game game; game.run();
        └─ создать окно (SFML)
           ├─ загрузить ресурсы (шрифт) — с проверкой
           ├─ загрузить рекорд
           ├─ игровой цикл:
           │    события → update(dt) [модель] → render() [SFML] → display()
           └─ при выходе: сохранить рекорд, закрыть окно
```

Ресурсы владеются `Game` (RAII); объекты — `std::vector` по значению
(без ручных указателей). Пул объектов вводится в th53 как оптимизация.

## 24. Возможные риски

- перерастание игры в «весь код в `main.cpp`» → дисциплина слоёв (п.18);
- зависимость движения от FPS → только `update(dt)`;
- загрузка ресурсов падает (нет файла) → обработка ошибок обязательна;
- тесты с окном в CI не запускаются → логика в модели, smoke-тест под флагом.

## 25. Подводные камни

- коллизия считается после «телепорта» на `speed*dt` — на высоких скоростях
  пролетание сквозь предмет (нужен swept/маленький шаг; разбор — th22);
- рекорд-путь «текущей директории» — при запуске из IDE отличается от запуска
  из терминала: путь строить от исполняемого файла;
- не сохранять промежуточное состояние счёта на каждый кадр (диск).

## 34. Связь с профессиональной разработкой

Этот проект — «движок в миниатюре»: игра отделена от рендера, время
инъектируется, состояние явное, данные тестируются. Приём «модель без UI»
переносится на крупные проекты напрямую; здесь он появляется максимально рано,
чтобы войти в привычку до того, как проект станет сложным.
