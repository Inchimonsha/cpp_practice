# AGENTS.md

Правила и соглашения, действующие в этом репозитории. Обязательны для ИИ-агентов
и людей, которые развивают курс. Документ актуален — обновляйте его при принятии
новых архитектурных решений.

---

## 1. Назначение репозитория

Учебный курс «C++ и Lua: разработка 2D-игр и игровых песочниц (SFML)».
Структура описана в `README.md`, план — в `ROADMAP.md`.

## 2. Зафиксированные технические решения

| Решение | Значение | Комментарий |
|---|---|---|
| Стандарт C++ | **C++20** | Проверено на GCC 16.2 (MSYS2 `ucrt64`). `std::print` недоступен (GCC < 14) — использовать `<iostream>`. |
| SFML | **3.1.0** (пребилты) | API SFML 3: `pollEvent()` возвращает `std::optional<sf::Event>`, события — `std::variant` (`event->is<...>()`, `event->getIf<...>()`). |
| Windows-тулчейн для SFML | **UCRT-базированный MinGW** (MSYS2 `ucrt64` / winlibs UCRT, GCC ≥ 14) | Пребилт SFML собран под UCRT (winlibs GCC 14.2). msvcrt-тулчейн собирает и линкует SFML-приложение, но оно падает при запуске (`0xC0000005`, heap-коррупция при освобождении памяти из чужой CRT — проверено). `cmake/sfml.cmake` на POST_BUILD копирует рядом с exe DLL пребилта и рантайм компилятора (`libstdc++-6.dll`, `libgcc_s_seh-1.dll`, `libwinpthread-1.dll`). |
| Lua | **5.4.9** | Выбран ради совместимости с экосистемой (sol2, большинство C-библиотек). Lua 5.5 существует, но не является целевым. |
| Сборка | **CMake ≥ 3.20** | Корневой `CMakeLists.txt` подключает `common`, упражнения и проекты. |
| Язык кода | **C++** (комментарии/строки в примерах допускаются на русском) | Имена идентификаторов — английские. |
| Язык документации | **Русский** | Термины и API — в оригинале, с пояснением при первом упоминании. |
| Тестовый фреймворк | минимальный хедер-онли `common/include/cpp_course/test.hpp` | Без внешних зависимостей. Зрелые фреймворки (doctest/Catch2/gtest) допускаются, если явно задокументированы. |
| Зависимости | скачиваются в `third_party/` (в `.gitignore`) | См. `tools/fetch_deps.py`. |

## 3. Порядок работы (обязателен)

1. Сначала читайте `AGENTS.md` и `ROADMAP.md`.
2. Работайте итеративно блоками: каркас → теория → задания → проекты → проверки.
3. После каждого блока: проверьте ссылки, команды сборки, примеры; обновите
   `ROADMAP.md`, `CHECKLIST.md`, `CHANGELOG.md`.
4. Не создавайте «пустые» учебные разделы. Раздел считается готовым только когда
   содержатся все обязательные файлы (проверяется валидатором).
5. Не удаляйте существующие файлы без явного разрешения пользователя.
6. Если в репозитории появился пользовательский код — интегрируйте его аккуратно
   и описывайте в изменений, а не перезаписывайте.

## 4. Требования к коду (C++)

- Современный C++20, без ручного `new`/`delete` без обоснования.
- `std::unique_ptr` — владение по умолчанию; `std::shared_ptr` — только при
  обоснованной совместной собственности.
- RAII, `const` correctness, небольшие функции, понятные интерфейсы.
- Разделение `.hpp` (объявления) и `.cpp` (реализация).
- Нет глобального изменяемого состояния без объяснения.
- Публичные интерфейсы документируются.
- Для каждого архитектурного решения — объяснение «какую проблему решает,
  какие альтернативы, недостатки, когда не применять».

## 5. Требования к коду (Lua)

- Скрипты имеют понятный API-контракт и пример использования из C++.
- Объясняется граница ответственности C++ и Lua.
- Явно описываются безопасность (sandboxing), версионирование API,
  совместимость скриптов, диагностика ошибок.

## 6. Требования к коду (SFML)

- Указывается версия (3.1.0) и требования сборки.
- Не полагаться на файлы, которых нет в репозитории.
- Обрабатывать ошибки загрузки ресурсов.
- Корректно обрабатывать события, учитывать `delta time`.
- Объяснять жизненный цикл окна; не смешивать без объяснения логику, ввод и
  рендеринг.

## 7. Стиль документации

- Пишите ясно, точно, профессионально. Никакой «мотивационной» воды.
- Не утверждайте, что код протестирован, если он не запускался.
- Не создавайте псевдокод там, где требуется рабочий код.
- Разделяйте: **обязательное / рекомендуемое / дополнительное / экспериментальное**.
- Для примеров указывайте стандарт C++ и версии библиотек.
- Не дублируйте объяснения: ссылайтесь на раздел, где тема уже раскрыта.

## 8. Распределение ответственности

- `theory/thNN_*` — обучающий нарратив + `examples/`, `cheatsheet.md`,
  `pitfalls.md`, `sources.md`.
- `exes/exNN_*` — постановка, `starter/`, `solution/`, `tests/`, `hints.md`,
  `review.md`.
- `prjs/prjNN_*` — полный каркас проекта с документацией и кодом.
- `common/` — переиспользуемый код только после ревью; изменения Changelog.

## 9. Проверки

Все проверки перечислены в `README.md`. Обязательные перед тем, как объявить
блок завершённым:

```bash
python tools/validators/check_structure.py
python tools/validators/check_links.py
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
```

## 10. Принятие решений при неоднозначности

1. Выбирайте наиболее практичный вариант.
2. Фиксируйте решение здесь и в соответствующей документации.
3. Не останавливайте работу из-за мелких неопределённостей.
4. Задавайте вопрос только при риске потери данных или фундаментально
   неправильной архитектуры.
