# th01 — Настройка проекта: компилятор, CMake, IDE, Git, сборка и запуск

Модуль 0. Организация разработки.

---

## 1. Название

«Настройка проекта» — первая тема курса. Она готовит рабочую среду и объясняет,
как из исходного кода получается запускаемая игра, как управлять версиями кода
и как отлаживать ошибки. Все последующие темы опираются на термины и команды
из этого раздела.

## 2. Цели обучения

После изучения темы студент:

- объясняет жизненный цикл сборки C++-программы (исходник → объектный файл →
  исполняемый файл);
- устанавливает и настраивает компилятор, CMake и IDE;
- создаёт проект с CMake, собирает и запускает его из командной строки;
- различает Debug и Release и понимает, зачем они нужны;
- использует базовые команды Git (инициализация, commit, ветки, push/pull);
- умеет читать диагностику компилятора и линкера и находить источник ошибки;
- знает, где искать документацию (cppreference, доки SFML/Lua) и как
  лицензировать ассеты.

## 3. Предварительные знания

Не требуются. Тема рассчитана на старт с нуля.

## 4. Почему тема важна в GameDev

Игра — большая программа с ресурсами, сборкой на несколько платформ и длинным
жизненным циклом. Настройка среды и порядок сборки определяют скорость итераций
разработки:

- **время сборки** напрямую влияет на частоту «попробовал — увидел изменение»;
- **Debug/Release** определяет, где легче находить баги, а где игра быстрая;
- **Git** избавляет от страха сломать игру: всегда можно откатиться;
- **CMake** позволяет собирать проект на Windows, Linux и macOS одинаково — это
  стандарт индустрии; сам SFML собирается именно CMake;
- лицензии ассетов защищают разработчика юридически: чужой шрифт или музыку
  нельзя просто положить в игру.

## 5. Теоретическое объяснение

### 5.1. Что происходит при сборке программы

C++-код не исполняется напрямую — его нужно превратить в машинный код.
Цепочка:

```
main.cpp ──► препроцессор ──► компилятор ──► объектный файл (.o / .obj)
main2.cpp ──► ... ──► объектный файл ─────────────┐
                                                  ▼
                                             ЛИНКЕР
                                                  │
                                                  ▼
                                      исполняемый файл (.exe / ELF / Mach-O)
                                      или библиотека (.dll / .a / .so / .dylib)
```

- **Препроцессор** обрабатывает директивы `#include`, `#define`, условия
  `#ifdef`. Вход — исходник, выход — «переведённый» текст для компилятора.
- **Компилятор** переводит C++-код в ассемблерные инструкции, а затем — в
  объектный файл с машинным кодом и метаданными о символах (функциях,
  глобальных переменных).
- **Линкер** собирает объектные файлы и библиотеки в один исполняемый файл:
  находит определения функций, расставляет адреса, проверяет, что нет
  конфликтов символов.

Отсюда вытекает классификация ошибок (см. раздел 12):

| Стадия | Что означает |
|---|---|
| ошибка компиляции | код не соответствует языку (синтаксис, типы) |
| ошибка линковки | функция объявлена, но не определена ни в одном объектном файле/библиотеке |
| ошибка времени выполнения | программа собралась, но упала или повела себя неправильно |

Важно: **компиляция — пофайловая**, линковка — итоговая. Частая правка одного
заголовка пересобирает много файлов; для больших проектов оптимизируют
зависимости заголовков (см. `th08_oop`, `th53_performance_data`).

### 5.2. Выбор стандарта C++

Стандарты: C++98/03 → C++11 → C++14 → C++17 → C++20 → C++23 → C++26 (ожидается
в 2026 году). Чем новее — тем больше возможностей, но тем новее должен быть
компилятор.

В курсе выбран **C++20** — разумный баланс:

- доступен в GCC ≥ 11, Clang ≥ 14, MSVC ≥ 19.29;
- даёт `std::optional`, `std::variant`, `std::span`, concepts, `std::ranges`,
  coroutines — всё это используется в курсе;
- SFML 3.1.0 требует не меньше C++17, так что C++20 полностью покрывает
  требования библиотеки;
- `std::print` (C++23) недоступен в GCC 13 — в курсе используется
  `<iostream>`.

**Правило курса:** код пишется на C++20. Фича новее фиксируется в `AGENTS.md`
и в конкретном примере.

### 5.3. Компиляторы

| Компилятор | Платформы | Особенности |
|---|---|---|
| GCC (`g++`) | Linux, Windows (MinGW-w64), macOS (через brew) | открытый, версии 13+ стабильны |
| Clang (`clang++`) | Linux, macOS, Windows | доходчивые диагностики, санитайзеры |
| MSVC (`cl`) | Windows (Visual Studio) | родной для Windows, интеграция SDK |

Для Windows-мира с GCC используется **MinGW-w64** — набор «GCC + минимальные
заголовки Windows», позволяющий собирать нативные EXE без Visual Studio.
Минус — две реализации C runtime: классическая **MSVCRT** и современная
**UCRT** (Universal CRT). Пребилты SFML собраны под UCRT, поэтому SFML-цели
собираются UCRT-тулчейном (MSYS2 `ucrt64` / winlibs UCRT, GCC ≥ 14).

Проверенное окружение курса: **MinGW-w64 UCRT GCC 16.2.0 (MSYS2 `ucrt64`) +
CMake 3.31.0**. msvcrt-тулчейн (например, bare GCC 13.2) слинкует
SFML-приложение, но оконные приложения падают при запуске из-за кросс-CRT
heap-коррупции — подробности в разделе 11 и `pitfalls.md`.

### 5.4. CMake — система сборки

CMake — не компилятор, а **генератор файлов сборки**: по файлу
`CMakeLists.txt` он создаёт сборочные файлы для конкретного генератора
(Makefiles, Ninja, проекты Visual Studio). Дальше запускается генератор.

Минимальный `CMakeLists.txt`:

```cmake
cmake_minimum_required(VERSION 3.20)
project(hello VERSION 0.1.0 LANGUAGES CXX)

add_executable(hello main.cpp)
```

Типовой цикл из терминала:

```bash
cmake -S . -B build          # конфигурация: читает CMakeLists.txt, создаёт build/
cmake --build build          # сборка
./build/hello.exe            # запуск (Windows)
```

Основные понятия CMake:

- **target** — библиотека или исполняемый файл;
- `add_executable(...)`, `add_library(...)` — объявление таргетов;
- `target_link_libraries(...)` — связи между целями;
- `target_include_directories(...)` — пути к заголовкам;
- кэш-переменные (`-DИМЯ=значение`) — настройки, например
  `-DCMAKE_BUILD_TYPE=Release`.

В корне курса `CMakeLists.txt` объявляет интерфейсный target `cpp_course_flags`
(стандарт C++20 + предупреждения), а `cmake/sfml.cmake` и `cmake/lua.cmake`
создают таргеты `cpp_course::sfml` и `cpp_course::lua`, от которых зависят
задания и проекты.

### 5.5. IDE

IDE нужна для навигации, автозавершения, отладчика и рефакторинга.

| IDE | Плюсы | Минусы |
|---|---|---|
| Visual Studio Code + C/C++, CMake Tools, clangd | бесплатно, кроссплатформенно, быстро | требует настройки |
| Visual Studio (Windows) | лучший отладчик Windows | только Windows, тяжёлая |
| CLion | сильная поддержка CMake | платная |
| Qt Creator | бесплатный, поддерживает CMake | меньше функций |

**Рекомендация курса:** VS Code + расширение CMake Tools; для навигации по коду
— языковой сервер clangd.

### 5.6. Git и удалённые репозитории

Git — система контроля версий. Основная единица — **коммит** (снимок состояния
проекта с сообщением). История — граф коммитов с ветками.

Основные команды:

```bash
git init                        # создать репозиторий
git status                      # текущее состояние
git add файл                    # добавить файлы в индекс (staging)
git commit -m "сообщение"       # зафиксировать
git log --oneline               # история
git branch имя                  # новая ветка
git checkout имя                # переключиться на ветку
git merge имя                   # слить ветку в текущую
git remote add origin <url>     # привязать удалённый репозиторий
git push -u origin main         # отправить ветку на сервер
git pull                        # получить обновления
```

Советы для курса:

- один коммит — одна логическая правка; сообщение — глагол в повелительном
  наклонении («добавить счёт очков»);
- не коммитить `build/`, `third_party/`, артефакты — они в `.gitignore`;
- приняты **семантические коммиты** (см. `th48_git_workflow`): `feat:`, `fix:`,
  `docs:`, `test:` и т. п.

### 5.7. Структура игрового проекта

Игровой проект делится на код, ресурсы и документацию:

```
игра/
├── CMakeLists.txt      ← сборка
├── src/                ← реализация
├── include/            ← публичные заголовки
├── assets/             ← шрифты, текстуры, звуки, данные
├── tests/              ← тесты
└── docs/               ← документация
```

Причины разделения: ресурсы не попадают в код (легче менять баланс и
локализацию), публичные заголовки отделены от реализации (меньше пересборка,
интерфейс виден явно), тесты живут отдельно (проще запускать в CI). Развитие
структуры — в `th32_resources_di` и `th41_sandbox_architecture`.

### 5.8. Debug и Release

| Параметр | Debug | Release |
|---|---|---|
| Оптимизация | нет (`-O0`) | агрессивная (`-O2`/`-O3`, MSVC `/O2`) |
| Отладочные символы | полные | обычно включаются отдельно |
| `NDEBUG` | не задан | задан (отключает `assert`) |
| Скорость | медленно | быстро |
| Для чего | отладка, тесты | поставка, замеры производительности |

Правило курса: ежедневная разработка — **Debug**, финальные замеры и упаковка —
**Release**. Баг, видимый только в Release, — сигнал неопределённого поведения
(UB) в коде: оптимизация переупорядочивает код и вскрывает зависимость от
неописанного поведения (см. `th14_cpp_performance_intro`, `th50_profiling_debugging`).

В CMake тип сборки задаётся так:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
```

### 5.9. Терминал

Терминал — «рабочий язык» разработчика. Базовые команды:

| Действие | PowerShell (Windows) | bash/zsh (Linux/macOS) |
|---|---|---|
| текущий каталог | `pwd` | `pwd` |
| список файлов | `ls` | `ls` |
| перейти в каталог | `cd путь` | `cd путь` |
| создать файл | `New-Item` | `touch` |
| копировать | `Copy-Item` | `cp` |
| переместить | `Move-Item` | `mv` |
| удалить | `Remove-Item` | `rm` |
| переменная | `$env:ИМЯ = "значение"` | `export ИМЯ=значение` |

В курсе команды даются в общем виде и дублируются для обеих сред там, где это
важно.

### 5.10. Сборка и запуск в курсе

Полный цикл (см. также корневой `README.md`):

```bash
# 1. Зависимости (SFML, Lua) — один раз
python tools/fetch_deps.py

# 2. Конфигурация и сборка
cmake -S . -B build
cmake --build build --config Release

# 3. Тесты
ctest --test-dir build --output-on-failure

# 4. Валидаторы курса
python tools/validators/check_structure.py
python tools/validators/check_links.py
```

Запуск конкретной цели:

```bash
cmake --build build --target ИМЯ_ЦЕЛИ   # собрать только её
./build/ИМЯ_ЦЕЛИ.exe                    # запустить
```

### 5.11. Диагностика ошибок

Порядок действий при ошибке:

1. Прочитайте первую строку сообщения: обычно там файл и строка.
2. Определите стадию: компиляция / линковка / рантайм.
3. Ищите «первопричину»: у GCC диагностика может тянуть за собой десятки
   производных ошибок — важно самое раннее вхождение.
4. Упростите: удалите половину кода и проверьте, что компилируется (бинарный
   поиск по источнику).
5. Сводите баг к минимуму: 10 строк на воспроизведение — половина решения.

Осознанный процесс — «гипотеза → эксперимент → вывод», а не перебор вариантов.

### 5.12. Форматирование кода

Единый стиль обязателен: иначе в `git diff` смешаются содержательные правки и
переформатирования. Правила стиля — в `AGENTS.md`; автоматическое
форматирование — **clang-format** (конфиг по умолчанию: 4 пробела, LLVM-база):

```bash
clang-format -i main.cpp       # переформатировать файл
clang-format --dry-run main.cpp  # проверить без записи
```

### 5.14. Зависимости и лицензирование ассетов

- **Зависимости** бывают пребилтами и сборкой из исходников. Риск пребилта —
  ABI-несовместимость (раздел 11). Курс скачивает зависимости в `third_party/`
  скриптом `tools/fetch_deps.py` с проверкой SHA-256.
- **Лицензии ассетов**: файл без лицензии — «все права защищены». Для игры
  нужны ассеты с правом использования и распространения (Public Domain, CC0,
  CC-BY, свободные шрифты и т. п.). Автор и лицензия фиксируются рядом с
  ассетом (`assets/README.md`). Подробно — в `th51_ci_release`.

### 5.15. Организация рабочего процесса

Методика курса: тема → мини-практика → задание → проект → проверки. Рабочий
ритм:

1. Прочитать тему и выполнить мини-практику.
2. Решить задание: сначала сам, потом подсказки, потом сверка с разбором.
3. Продвигать свой проект по milestones из `requirements.md`.
4. После блока — `git commit` и обновление `CHECKLIST.md`.

## 6. Синтаксис

Синтаксис «нулевой» темы — это команды shell и файл `CMakeLists.txt`:

```cmake
cmake_minimum_required(VERSION 3.20)   # минимальная версия
project(имя VERSION 1.0)               # объявление проекта
add_executable(имя source.cpp)         # исполняемый файл
add_library(имя SHARED source.cpp)     # библиотека
target_link_libraries(имя PUBLIC dep)  # зависимость
option(ФЛАГ "описание" ON)             # опция сборки
```

```bash
cmake -S . -B build        # создать конфигурацию
cmake --build build        # собрать
ctest --test-dir build     # прогнать тесты
git add . && git commit -m "feat: ..."
```

C++-минимум для проверки окружения:

```cpp
#include <iostream>

int main() {
    std::cout << "Hello, game!\n";
    return 0;
}
```

## 9. Применение в 2D-играх

- **Структура проекта** определяет, где лежат спрайты и звуки и как сборка их
  находит; без этого игра «не видит» свои же ресурсы при запуске.
- **Debug/Release** влияет на скорость отладки игрового цикла: в Debug удобно
  ловить баги логики, в Release — проверять итоговую производительность.
- **Git** позволяет безопасно экспериментировать с балансом и уровнями.
- **Терминал + логирование** (`common`-логгер) — первый инструмент
  диагностики «почему игра зависла или упала» до подключения отладчика.

## 10. Применение в песочницах

В песочницах (генерация мира, чанки, день/ночь) критичны:

- **время сборки итерации** — генерацию и симуляцию нужно часто проверять;
- **структура папок ресурсов** — процедурные миры и конфигурации живут в
  `assets/data/` и загружаются по правилам, установленным здесь;
- **Git-история** баланса и генерации — вернуть «тот самый» вариант мира без
  переписывания блока инструкций;
- **диагностика по логам** — при больших мирах краши воспроизводятся по логу,
  а не «глазами».

## 11. Взаимодействие с SFML

SFML поставляется библиотекой, поэтому важны ABI-соображения:

- **ABI** (application binary interface) — соглашение на уровне бинарного кода:
  как выглядят структуры в памяти, как вызываются функции, какие имена у
  символов. Программа и пребилт должны совпадать по компилятору (GCC vs MSVC),
  разрядности (32/64) и CRT (MSVCRT vs UCRT).
- **Таблица соответствия** для пребилтов SFML 3.1.0:

  | Компилятор | Пребилт | Запуск оконного приложения |
  |---|---|---|
  | MinGW-w64 UCRT GCC ≥ 14 (MSYS2 `ucrt64` / winlibs) | `SFML-3.1.0-windows-gcc-14.2.0-mingw-64-bit` | работает |
  | MinGW-w64 MSVCRT GCC 13.x | тот же пребилт | **линкуется, но падает при запуске** (кросс-CRT heap) |
  | MSVC 17 (Visual Studio 2022) | `SFML-3.1.0-windows-vc17-64-bit` | работает |

  Итог для Windows: **SFML-цели собирайте только UCRT-тулчейном** —
  остальные языковые части курса можно компилировать любым C++20-компилятором.
  Рантайм-DLL MinGW (`libstdc++-6.dll`, `libgcc_s_seh-1.dll`,
  `libwinpthread-1.dll`) должны быть той же версии, что и ваш UCRT-g++
  (в курсе их копирует `cmake/sfml.cmake` на POST_BUILD).

- При рассогласовании версий стоит собрать SFML из исходников (сам SFML
  собирается через CMake) или сменить инструментарий на рекомендованный.
- Плагины и ресурсы SFML подгружаются из файлов рядом с исполняемым файлом;
  пребилт курса автоматически копирует DLL в каталог сборки
  (`cmake/sfml.cmake`).

Сборка SFML-зависимой цели:

```bash
cmake -S . -B build -DCPP_COURSE_ENABLE_SFML=ON
cmake --build build
ctest --test-dir build --output-on-failure
```

## 12. Типичные ошибки

Кратко; развёрнутый список диагностик — в [pitfalls.md](pitfalls.md).

1. **Не читать первую строку ошибки** — дальше идут производные «шлейфы».
2. **Линковочные ошибки путать с компиляционными**: «undefined reference
   to...» — функция объявлена, но не определена/не прилинкована библиотека.
3. **Забывать, что `main` возвращает код** — по нему CI и оболочки понимают,
   успешен ли запуск.
4. **Коммитить `build/` и `third_party/`** — артефакты и загруженные
   зависимости не должны быть в репозитории.
5. **Отлаживать в Release** — нужно сначала Debug.
6. **Пропускать предупреждения** — многие из них указывают на реальные баги.

## 13. Подводные камни

Кратко; развёрнутый список — в [pitfalls.md](pitfalls.md).

- **Регистр путей** на Windows: компилятор/FS могут быть регистрозависимы или
  нет — пути в CMake должны совпадать.
- **`assert` исчезает в Release** (макрос `NDEBUG`) — не пишите «важную» логику
  в `assert`.
- **Порядок `-l` библиотек** при ручной линковке GCC: библиотеки должны идти
  после объектных файлов, которые их используют.
- **Смена битности/компилятора** — требует пересборки всех пребилтов (ABI).
- **Запуск из IDE vs из терминала** — рабочая директория разная; пути к
  ресурсам логируйте.

## 14. Советы по проектированию

- Собирайте «проверку окружения» (`build_info.cpp`) первым проектом —
  она докажет, что цепочка инструментов работает.
- Устанавливайте `CMAKE_BUILD_TYPE` явно и не смешивайте конфигурации в одной
  папке (`build-debug/`, `build-release/`).
- Один коммит — одна правка; пишите осмысленные сообщения с префиксами
  `feat:`/`fix:`/`docs:`/`test:`.
- Автоформат включайте в редактор (format-on-save), а не «по памяти».
- Ссылки на ресурсы держите относительно исполняемого файла, а не текущей
  директории.
- Обновляйте `CHECKLIST.md` после каждого блока — это история собственного
  прогресса и приём самооценки.
